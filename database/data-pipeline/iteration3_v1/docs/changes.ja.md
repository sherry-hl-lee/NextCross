# 6か月の運用と引き継ぎに向けた変更

2026-10-06 時点の実装内容。方針は、**取得・検証を自動化し、人が確認した候補だけを公開する**ことです。事故データは 2021–2025 年を維持し、2027 年 9 月に初めて 2022–2026 年への更新候補を作ります。年が変わっただけで本番データは切り替わりません。

この変更はリポジトリ内の実装です。本番 DB の更新、GitHub の設定変更、バックエンドのデプロイ、後任者による受入確認は別の作業です。現在の本番が 9 テーブルであることは利用者から確認済みですが、今回、本番の接続・行数・権限を再検査していません。

## 何が変わるか

| 対象 | これまで | 変更後 |
| --- | --- | --- |
| データ更新 | 速度・事故・カレンダーを同じ実行で準備・公開 | データごとに準備・公開。翌年カレンダーの失敗が速度更新を止めない |
| 本番反映 | deploy 実行中に作成した一式を反映 | 保存済み候補の ID、元の実行、ハッシュを確認して、その候補だけを反映 |
| 事故データ | 通常の全データ更新に含まれる | 2027 年から毎年 9 月に 5 年分をまとめて再計算。同じ対象年の別候補を通常更新で再公開できない |
| カレンダー補正 | 公式 CSV の重複などで検証停止 | 原本を保存し、修正版・根拠 URL・確認日・担当者・理由を別に記録して検証 |
| 未確定の祝日 | 年全体がそろわないと公開不可 | 確認済みの開始日・終了日を明示した候補を作成可能。期間を守るバックエンドが必要 |
| 保管 | Actions の一時 artifact が中心 | 候補と更新予定を公開前に GitHub Release へ保存。公開結果も記録し、結果不明の実行が残れば次の公開・復元を停止 |
| DB とメール履歴 | 運用担当者が影響範囲を把握する必要がある | 通常公開では DDL を実行せず、対象データだけを更新。メール関連 2 テーブルの保持を回帰テスト |
| 障害対応 | 個別の操作手順に依存 | 読み取り専用の状態確認、`iteration2_v2` の 9 テーブルのバックアップ、検証用 DB への復元、担当者表を追加 |

DB のスキーマ名は引き続き `iteration2_v2`、コードは `iteration3_v1` です。テーブルを増やす変更はありません。カレンダーの期間情報は既存の `calendar_coverage.source_manifest` に保存します。

バックアップ範囲は利用者の指定どおり **`iteration2_v2` のみ**です。`iteration1_v2.notification_event` は一時的な保管場所として意図的に対象外とします。通知先テーブルの移行や、旧テーブルの別バックアップは今回の導入条件にしません。バックアップで保持する通知・送信履歴は `iteration2_v2` 内の 2 テーブルに限ります。

## GitHub Actions はいつ動くか

| タイミング | 自動で行うこと | 本番への書き込み |
| --- | --- | --- |
| パイプライン関連の PR | 単体テストと検証用 PostGIS のテスト | なし |
| 毎月 5 日 01:23 UTC | 速度、今年・翌年のカレンダーを別々の実行で取得・検証 | なし |
| 2027 年以降の 9 月の月次実行 | 上記に加え、事故の年次更新候補を作成 | なし |
| 毎週火曜 02:17 UTC | カレンダーの先 90 日、DB 容量、事故の更新漏れ、最近の実行結果を確認 | なし |
| 人が `operation=publish` を実行 | レビュー済みの候補を保存・照合し、選んだデータだけを反映 | あり |

**main への merge 自体ではデータは公開されません。** 定期実行の設定はこの workflow が既定ブランチへ入ってから有効になります。実行には Actions と必要な権限が有効であることが必要です。週次の DB 確認には読み取り専用の `NEON_READ_ONLY_DATABASE_URL` を repository secret に設定します。公開は既存の `neon-production` と `NEON_DIRECT_DATABASE_URL` を利用します。

GitHub の定期実行には遅延・未実行の可能性があるため、担当者が Actions の失敗通知と最終実行日を確認します。バックアップや障害対応まで無人化したものではありません。時刻は UTC 固定なので Melbourne の表示時刻は夏時間で変わります。

## 事故データの年次更新

| 公開時期 | 更新候補の対象期間 |
| --- | --- |
| 現在から 2027 年 8 月まで | 受入済みの 2021-01-01 ～ 2025-12-31 を維持 |
| 2027 年 9 月 | 2022-01-01 ～ 2026-12-31 |
| 2028 年 9 月 | 2023-01-01 ～ 2027-12-31 |
| 以降 | 毎年 9 月に 1 年進めた 5 年間 |

元データの対象期間、60 か月分の存在、座標欠損、件数の大幅減少を検査します。公式ソースに必要な範囲がまだそろっていなければ旧版を維持し、人が調査します。公開した期間は DB と公開記録から判断します。ロールバック後も公開履歴を参照するため、同じ年の別候補で無意識に置き換えることを防ぎます。

元の事故 CSV・位置情報 CSV・取得メタデータ・生成済み出力を一緒に保存します。2021–2025 年の手元の原本を保存済み候補にする手順も用意し、後から更新された公開 URL の再取得に復旧を依存させません。

手元の旧位置情報メタデータには対象期間が記録されていないため、旧 baseline の保存時だけ明示的な警告を残します。日付を後から書き足すことはせず、年次更新の候補には期間確認を要求します。また、9 月の更新を逃しても翌年 8 月までは直近の 9 月分を遅れて公開できます。

## カレンダーは一部手動でよい

`New Year's Day 2027-01-01` の重複は、公式情報を照合し、修正版から余分な行を除く運用が可能です。原本を上書きせず、何を変更したかを記録します。未発表の AFL 祝日などは推測で追加しません。

例えば 2027 年前半だけを確認できた場合、明示した終了日までの `READY_BOUNDED` 候補を作れます。期間外を「祝日ではない」と見なさないよう、バックエンドの速度ルール判定にも期間チェックを追加しました。日付をまたぐルールでは、判定に使う前日のカレンダーも確認します。従来の確認済み通年カレンダーも利用できます。

バックエンドの変更先は別リポジトリの `Backen_I2_V2` です。**バックエンドを先にデプロイ・確認してから**、限定期間の公開時に `allow_bounded_calendar=true` を指定します。初期値は false で、対応前の誤公開を防ぎます。実際の 2027 年補正ファイルの確認・受入と本番公開は運用手順として残ります。

## Backend のコード変更を詳しく見る

実行処理を変更・追加したのは `Backen_I2_V2/app/` 内の 3 ファイルです。
現在の `backend/Backen_I2_V2` の checkout に実装を統合します。
この説明は利用者が commit・push・PR で反映するローカル実装の状態で、本番への
デプロイ済みを意味しません。

| ファイル | 変更内容 | 必要な理由 |
| --- | --- | --- |
| `calendar_coverage.py`（新規） | `calendar_covers(day, coverage)` で日付、schema、policy、build ID、status、期間の整合性を確認 | 年の登録だけでは、その年の全日付を確認済みと判断できないため |
| `speed_repository.py` | 既存の `year, build_id` に加えて `policy_version, source_manifest` を取得 | 開始日・終了日・確認状態が既存の `source_manifest` に保存されるため |
| `speed_rules.py` | 年の存在確認を `calendar_covers(day, coverage)` の呼び出しに変更 | 学校日・祝日に依存する速度ルールに、実際の確認済み期間を適用するため |

以前の判定の中心は `if day.year not in coverage:` でした。これでは、2027 年の
coverage 行が 1 件あれば、2027 年のどの日でも判定に進めてしまいます。
変更後は `if not calendar_covers(day, coverage):` とし、期間外・未対応の policy・
不正な manifest の場合に既存の `calendar_out_of_coverage` を返します。
その結果、該当する速度判定は `unknown` になります。

例えば **2027-01-01 ～ 2027-04-30** が確認済みなら、その範囲内では通常の
学校日・祝日判定へ進みます。**2027-05-01** は確認済み期間外として扱い、
日付情報がないことを根拠に「学校日ではない」「通常速度でよい」とは判断しません。
この日付は挙動の説明用で、実際の公開済みカレンダーを示すものではありません。

`calendar_covers` は、従来の schema 3 の通年 `READY` と、手動レビューを残す
schema 4 の通年 `READY`／期間限定 `READY_BOUNDED` に対応します。期間の両端は
含みます。未確認 AFL の情報がある場合は、その最も早い可能日より前までしか
確認済みとしません。公式情報の収集・修正・根拠確認はパイプライン側で行い、
Backend はリクエスト時に公開済みの契約を確かめます。

日付をまたぐ速度ルールは、以前からルール開始日の曜日を使っていました。
今回の期間チェックもその日付調整の**後**に入ります。例えば 1 月 1 日の
深夜でも、12 月 31 日に始まったルールなら前年 12 月 31 日の coverage を確認します。

DB 読み取りは既存の読み取り専用 `REPEATABLE READ` トランザクションを使います。
カレンダー行と manifest を同じ状態から読むので、途中の公開で旧データと
新しい期間情報が混ざることを避けます。今回そのトランザクション自体を新設した
わけではなく、同じ枠内で取得する情報を増やしました。

定数の速度、カレンダーが不要な曜日・時間の判定、メール送信、事故の集計、API の
エンドポイントとレスポンス項目には今回の変更を加えていません。テストでは
期間の端・期間外・年またぎ・旧通年データとの互換性・不正な manifest の拒否を
確認しています。

## 引き継ぎ前に完了させること

1. バックエンドとパイプラインの変更をレビューし、それぞれ反映する。ホスティング側の実際の root directory も確認する。
2. 現行の原本・生成物・`iteration2_v2` の 9 テーブルのバックアップを保存し、後任者が検証用 DB への復元を実演する。
3. 必要な 2027 年の期間を公式情報で確認し、補正候補をレビューして手動公開する。
4. 読み取り専用 secret、Actions の権限、失敗通知、アカウント・課金・保守の担当者を設定する。
5. Support / Maintenance 文書へ下記の手順と検証記録を組み込み、Product 文書・知識移管・mentor sign-off・提出先を完成させる。

今回の文書はガイドラインに必要な運用・保守情報の土台です。プロダクト全体の Handover Package や受入署名まで完了したという意味ではありません。
